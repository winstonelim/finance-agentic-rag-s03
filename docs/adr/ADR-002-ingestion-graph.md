# ADR-002. 인제스천에 LangGraph를 쓰되, 문서당 LLM 루프는 두지 않는다

- 상태: **채택**
- 날짜: 2026-10-01
- 관련: `src/finrag/ingestion/graph.py`, `src/finrag/ingestion/nodes.py`

---

## 맥락

49개 문서는 PDF, 스캔본, HWP/HWPX 등 형식과 품질이 서로 달라 하나의 파서만으로
안정적으로 처리할 수 없었다. 정상 문서는 바로 통과시키되 문제가 있는 문서만 재파싱,
OCR 또는 사람 검토로 분기하고, 각 문서가 어떤 이유로 실패했는지 재현 가능하게 남겨야 했다.

측정된 사실:

| 무엇 | 값 | 출처 |
|---|---|---|
| 게이트 판정 | pass 40, reparse 5, ocr 2, fail 2 | `data/ingest_report.json` |
| 전체 처리 결과 | 49문서, done 45, failed 4, 3,689청크 | `data/ingest_report.json` |

사람 검토 큐에는 `law_silson_std_hwp`, `fss_deposit_terms_2022_hwpx`,
`knia_4000`이 남았다. 앞의 두 문서는 지원하지 않는 HWP/HWPX 형식이고,
`knia_4000`은 재파싱으로도 복구되지 않아 LLM 복구 단계까지 갔으나
API 키가 없어 복구를 건너뛰었다.

## 대안

| # | 대안 | 장점 | 단점 | 왜 안 골랐나 |
|---|---|---|---|---|
| A | 문서마다 LLM으로 읽고 정리 | 다양한 문서에 유연함 | 비용과 지연이 크고 결과가 비결정적임 | 모든 문서에 LLM을 호출할 필요가 없고 재현성이 낮음 |
| B | Python if문으로 직접 분기 | 단순하고 빠르게 구현 가능 | 분기가 늘수록 흐름과 실패 경로를 추적하기 어려움 | 재파싱·OCR·실패 경로가 추가될수록 유지보수가 어려움 |
| C | LangGraph로 명시적 상태 전이 | 분기와 실패 경로가 명확하고 테스트와 추적이 쉬움 | 그래프와 상태 정의가 추가로 필요함 | **← 골랐다** |

## 결정

> 인제스천 흐름은 LangGraph의 명시적 상태 전이로 구성하고, 문서당 반복적인 LLM 루프는 두지 않으며 LLM 복구는 결정적 파서와 OCR이 실패한 경우에만 마지막 수단으로 사용한다.

## 근거 지표

| 지표 | 전 | 후 | 차이 |
|---|---|---|---|
| 전체 처리 문서 | 측정하지 않았다 | 49건 | 측정하지 않았다 |
| 생성 청크 | 측정하지 않았다 | 3,689개 | 측정하지 않았다 |

측정 방법: `전체 코퍼스를 인제스천한 뒤 ingest_report.json의 경로·판정·청크 수를 집계`
재현 명령: `make ingest`

## 대가

| 잃은 것 | 얼마나 | 받아들일 만한 이유 |
|---|---|---|
| 구현 단순성 | 그래프 노드와 라우터 코드가 추가됨 | 실패 원인과 처리 경로를 명시적으로 추적할 수 있음 |
| 자동 복구 범위 | 사람 검토 큐 3건이 남음 | 잘못 복구한 내용을 근거로 사용하는 것보다 안전함 |

## 되돌릴 조건

- [ ] 인제스천 성공률이 `90%` 아래로 내려가면
- [ ] 저비용·저지연 LLM을 안정적으로 사용할 수 있게 되면
- [ ] 문서 수가 `500건`을 넘으면
- [ ] 반복적으로 사람이 처리하는 동일 유형의 실패 문서가 증가하면 문서당 LLM 복구 전략을 다시 검토한다.

되돌리는 비용: 그래프의 복구 노드를 교체하고 전체 문서를 다시 인제스천해야 한다.

## 결과

LangGraph 기반 인제스천으로 49개 문서를 처리해 3,689개 청크를 생성했다.
45개 문서는 정상 처리되었고 4개 문서는 사람 검토 큐로 분리되었다.
게이트에서는 pass 40건, reparse 5건, ocr 2건, fail 2건으로 분기되어
문서 상태에 따라 필요한 처리 경로만 수행하도록 구성되었다.
